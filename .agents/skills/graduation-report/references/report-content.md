# 内容与交付规范

## 章节

| 部分 | 内容 |
| --- | --- |
| 封面 | 学校、项目、专业、学生、学号、教师、地点和时间，按模板填写 |
| 摘要与关键词 | 背景、目标、实际方法、功能与成果；关键词一般3—5个；需要时配对应外文 |
| 目录 | 自动生成，与最终标题和页码一致 |
| 引言 | 选题原因、已有应用或研究、待解决问题、目标及意义 |
| 相关技术 | 实际技术版本、用途、选型依据 |
| 需求分析 | 角色、权限、功能、业务限制、非功能需求及核心流程 |
| 系统设计 | 总体架构、模块、实体关系、表结构、关键状态和规则 |
| 系统实现 | 按模块说明实际功能、操作、关键逻辑及运行截图 |
| 系统测试 | 环境、方法、可复现用例、真实结果、缺陷与限制 |
| 结束语 | 完成工作、不足及改进，不新增未经验证成果 |
| 致谢 | 真实经历，不编造人名或指导关系 |
| 参考文献 | 实际引用且核验的资料，正文引用与条目对应 |
| 附录 | 按学校或用户要求保留必要代码、长表或接口资料；默认不含部署与材料交付说明 |

章节可合并或调整。学校未规定时不强制某个章数或字数。

部署启动步骤、配套文件清单、生成过程及封面待补信息属于论文外的交付文档，默认不生成“部署与材料说明”附录，也不混入致谢、结束语等学术章节；学校或用户明确要求的内容除外。

## 参考文献选取与引用

- 约5000字的软件设计报告可先按约10条规划，兼顾直接相关的业务期刊、支撑技术设计的专著和少量官方文档；这是本次用户确认的适用规模建议，不是学校固定数量。只保留真实、相关且能在正文实际使用的资料，不为凑数加入文献，不仅列三份框架入门网页。
- 优先选择座位预约、资源使用、签到或业务管理等与选题直接相关的研究，技术资料与实际栈对应；不因都使用Spring Boot就引用无关业务论文。
- 期刊核对作者、题名、年份、卷期、完整页码和实际存在的DOI；图书核对作者、版次、出版社、出版年及ISBN。印刷年不等同于初版出版年。官方文档尽量选择与项目依赖对应的版本，并记录真实访问日期。
- 用期刊原始记录、出版社官网、高校原始馆藏书目或官方技术文档核验；发现转载作者或页码冲突时优先回到原始记录，无法消解的条目不作为已确认文献。
- 区分书目核验、摘要阅读和全文阅读。只读到摘要或简介时，引用不得超出其公开支持范围，不声称阅读全文，也不编造具体引文页码。
- 检索阶段提供候选条目、来源链接、核验层级和适合引用的位置。用户明确要求“先找，确认后再写”时，候选阶段不修改论文；确认后替换旧条目而非机械追加，并补充相关研究及正文引用。
- 按正文首次出现顺序编号，确保每条文献实际被引用，正文与文后条目一一对应。不得用外部文献替代项目自己的测试证据，也不得将文献中的传感器、短信、推荐等功能写成本项目已实现成果。
- 保留来源与核验记录在论文外，Word和Markdown同步；不把来源筛选过程或“待确认”等工作备注加入正式参考文献页。

## 致谢内容与篇幅

- 默认约300字、三段左右，语气自然、真诚、克制。可围绕学习与毕业设计感受、对教师同学家人的感谢、今后学习态度组织，不套用长篇抒情话或为凑篇幅重复感谢。
- 不从他人参考稿复制指导老师、班主任、人名、学号或家庭细节；没有用户提供的事实，不编造具体指导事件、逐次修改、答辩意见或私人经历。用户要求不披露身份时使用一般称谓。
- 致谢不写封面待补、文件目录、生成工具和交付流程等说明。仅感谢框架或官方文档的一句话通常不足以满足完整毕业报告的致谢需求。
- 用户最终修改优先；标题位置独立于正文缩进，采用所选模板或已确认的专用致谢标题样式，不能因使用Heading 1而继承普通章标题的两字缩进。

## 图表内容

用例图展示角色与功能；流程图展示正常、判断及异常路径；架构图展示真实部署或逻辑分层；功能图展示模块层级，避免与架构图混淆；E-R图展示实体、关系和基数；数据字典记录字段、类型、约束、默认值与业务含义；截图证明实际界面和结果。

完整项目至少解释一条核心业务在需求、设计、实现与测试中的对应关系。测试按项目覆盖登录、角色权限、归属、增删改查、状态变化及相关异常；没有执行的内容不写通过，没有性能实测不写响应时间或并发指标。

## 最终检查

- 角色、模块、字段、状态、技术与代码一致。
- 图表有正文引用与解释，源文件保留，插图清晰。
- 无旧项目文案、伪造数据、失效引用和未处理的占位符。
- 参考文献来源可查，引用支持对应论述。
- 字体、字号、颜色、间距、页边距、页码符合选定模板。
- 目录已更新，长表可读，图题不分离，所有页面经过版式检查。
- 未完成、未运行及未验证项在交付说明中如实列明，不将草稿称为已验证终稿。
