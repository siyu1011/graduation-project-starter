# 软件毕业设计报告

以真实项目为依据，形成需求、设计、实现、测试相互对应的报告。按用户请求选择完整报告、章节修订、图表、截图或格式检查模式，只执行所需范围；编写论文不自动授权修改业务系统、重置数据库或发布内容。

## 资料与格式选择

- 优先采用用户本次指定的学校模板和指导教师最新要求。
- 用户明确选择洛阳职业技术学院2026软件技术模板时，读取 [学校格式](references/luoyang-2026.md)。仅在用户选择该学校模板时采用其中数值，其他项目不得自动套用。
- 使用该学校封面时，执行学校格式中的“已确认封面标准”，并查看随技能保存的整页及信息栏参考图；信息栏采用用户确认的常规字重、等距行与等长对齐横线，优先于原方案中的加粗、空格下划线样式。
- 用户手动调整后的文档是当前排版依据。先读取实际段落及样式，区分直接格式和继承格式；洛阳模板的致谢标题沿用学校格式中的“已确认致谢样式”，不能重新套用带两字缩进的普通章标题。
- 未提供模板时采用一致的临时排版方案，注明它是建议；内容工作继续推进。
- 读取 [报告内容规范](references/report-content.md) 组织章节、图表和交付检查。
- 生成Word时使用环境可用的文档技能，遵循其文档创建及渲染要求；没有专用能力时保留可编辑源稿并如实报告限制。

## 核对项目事实

遵守目标仓库AGENTS.md，包括代码定位工具要求。先核对README、实际依赖、需求文档和数据库脚本，再定位相关实现。记录项目名称、技术版本、角色、权限、实体、核心业务状态及已实现范围。

在任务输出目录保存事实与证据记录，包含“事实或结论、代码/SQL/文档路径或运行证据、验证状态”。区分代码中存在、已运行验证、尚未验证；代码存在不能证明运行成功。缺少影响业务含义的资料时简洁询问，继续完成不依赖答案的部分。

## 编写与修订

按需求→设计→实现→测试建立对应关系，先写正文，再根据实际成果写摘要和结束语。用户只要求某一章节时，不扩写整篇。

论文默认不加入“部署与材料说明”等交付性质附录。启动命令、数据库导入、演示账号、配套文件目录、生成工具及封面待补等说明保存在论文外的README或交付记录中；仅当用户或学校模板明确要求时才纳入论文。技术性附录按实际需要保留，不把交付检查备注写入摘要、致谢或结束语。

每个核心模块说明使用角色、操作、业务约束、实现方式及结果。技术介绍解释实际选型用途；不堆砌框架百科。计划功能放到改进方向，不列入完成成果。

文献须实际可查且支持相应论述。核对来源后填写出版信息，正文与文后引用对应；不凭印象生成作者、书名、年份、DOI或网址。外部资料无法核对时明确待核验，不能作为已验证参考文献交付。

参考文献选取与致谢篇幅执行 [报告内容规范](references/report-content.md) 的具体规则：文献兼顾业务研究与技术依据，致谢默认约300字，不照搬参考稿人名和经历。用户要求先确认候选文献时，在确认前不写入论文。

## 图表制作

按内容选取用例图、流程图、架构图、功能模块图、E-R图、实体属性图、数据字典与测试表，不设固定数量。

完整软件类报告先按 [图表规划与核对](references/paper-diagrams.md) 检查角色操作、系统处理、功能结构、技术架构及数据设计是否都有足够表达。用户提供教师认可的参考论文时，对照其图表用途确认本项目的适用项；不能仅以已有E-R图、架构图或状态图为由省略流程图、功能结构图及实体属性图。具体清单按用户确认结果执行，不把单个项目的数量固化为所有论文的要求。

- 优先读取同级 `../diagram-design/SKILL.md` 使用项目随附的图表技能；没有本地副本时，再解析已安装的 `diagram-design:diagram-design` Skill。用于流程图、架构图、功能模块树、E-R图、数据库结构图、时序图和状态图，再按需读取所选图种的参考文件；不要硬编码插件版本路径。制作普通数据字典和测试记录时保留可编辑表格，不强行转成图片。
- 使用diagram-design时，将当前学校格式及用户已选的白底、黑字、清晰线条风格作为明确视觉输入；遵循其样式配置流程，不自动采用品牌配色或装饰字体。若确需补充风格选择，只询问缺失项，不重复确认已明确要求。
- 按其流程保留自包含HTML与内联SVG源文件。论文需要插图时，明确以SVG或PNG作为插图输出，并读取其导出参考、使用配套导出工具；检查中文字体、插入尺寸、连线及黑白打印效果。复杂图拆分时保留业务含义与关系，不为符合布局限制删掉实体或分支。
- 用例图、实体属性图等若没有对应图种规范，采用符合其语义的UML或实体属性表示法，不用近似图冒充。diagram-design不可用或不适合时使用可编辑的Mermaid、Graphviz或SVG等确定性工具，并说明替代方式；不以AI生图制作需要精确文字、关系和字段的技术图。
- 保存图源及适合插入报告的导出文件。架构箭头、流程分支、实体关系基数均须有项目依据；区分数据库外键与应用层逻辑关联。
- 图号、图题、正文引用一致，默认按章编号。学校未另定时图题在下、表题在上。
- 检查最终插入尺寸下的文字、线条、边界和黑白可读性。复杂E-R图可拆分并解释范围。
- 在证据记录中登记图号、文件、来源、对应章节和验证情况。

## 真实截图与测试

先核对启动步骤、服务端口和测试账号，使用可用的浏览器自动化工具实际操作。不同角色使用独立会话或退出后切换。不得将设计效果图、生成图片或静态页面当成真实业务截图。

按完整业务获取必要界面与结果，隐藏密码、令牌和个人敏感信息。保存截图原件，并记录角色、页面路径、操作、采集时间和图号；裁切不得改变结果含义。

测试记录包含前置条件、输入/步骤、预期、实际结果与结论。只有执行后才能判定通过；权限验证不能仅凭按钮隐藏。涉及写入操作使用隔离的测试数据，不自动重置或覆盖已有库。环境缺失时完成设计图及可做的正文，列明缺失截图和未验证流程。

## 输出与验收

按请求交付Markdown、Word、PDF或图表。完整报告默认保存于用户指定目录；未指定时用项目docs/graduation-report，避免覆盖已有成果。保存可编辑正文、图源、截图与证据记录，目录结构按实际需要创建。

交付前核对项目术语、图表编号、数据表字段、测试结论和参考文献；清除旧项目残留。Word/PDF须渲染并检查全部页面，更新目录和交叉引用；无法渲染时报告未完成版式验证，不声称终稿已验证。

最终说明生成文件、实际验证及剩余限制。仅生成规范或提纲时，不启动系统或执行业务测试。

用户宣布报告完工后，将其视为已定稿文件；仅检查或更新技能时只读报告，不重建文档、不刷新域或覆盖手工排版。后续明确修改时以最新文档为起点，保留授权范围外的格式与内容。
