# 基于 graduation-project-starter 的毕业设计开发 SOP

适用仓库：https://github.com/siyu1011/graduation-project-starter.git

整理日期：2026-10-16。目标：从通用底座交付一套本地可运行、有完整业务流程、具备真实验收证据的毕业设计系统。

本文依据底座提交 `dbf68e8` 的 README、仓库开发规范及项目实施经验整理，发布前已核对远程 README 和 AGENTS.md。复用时先核对当前提交、依赖及规范。

## 一、流程与执行原则

标准流程：建立项目 → 检查底座 → 确定选题 → 编写需求 → 确认视觉 → 制定计划 → 建立契约与数据库 → 按业务链开发 → 验收修复 → 构建交付。

- 默认交付源码、SQL、测试、启动说明、使用教程和验收记录。上线、论文、答辩材料按用户要求单独纳入范围。
- 每阶段留下可审阅产物；以实际检查作为完成依据，图片、计划和已写代码不能代替功能验收。
- 用户最新要求优先。需求明确后自主执行；涉及业务含义、已有数据处置或交付范围的缺口尽早询问。
- 环境不齐时继续不受影响的工作，分别记录通过、失败、跳过和未验证。
- 不固定套用自习室项目的时段、表结构、测试数量、性能指标或账号密码。
- 全程维护计划与进度，按可评审阶段提交 Git；不自动提交凭据、日志、依赖、缓存和构建产物。

## 二、阶段 0：建立独立项目

### 操作

1. 在目标项目目录克隆底座，确认不会覆盖已有文件。中文外层目录可用，包名、npm 名和 Maven artifactId 使用英文。
2. 核对 `.git`、当前分支、提交和工作区状态，记录底座提交号。
3. 先明确远程用途：框架仓库是来源，项目成果推送到用户指定的项目仓库；不要直接向底座 origin 推送业务改动。
4. 阅读 AGENTS.md。代码定位遵守项目 CodeGraph 规则：先尝试已有索引及工具，不可用时说明并用普通工具继续，不因此停工。

```powershell
# 在目标目录的父目录执行，目录名按项目修改
git clone https://github.com/siyu1011/graduation-project-starter.git my-project
cd my-project
git status --short
git remote -v
git rev-parse HEAD
# 确认分支尚不存在后创建
git switch -c codex/project-development
```

### 产出与出口

记录项目路径、来源提交、分支、远程用途；已有改动已识别并保留。

## 三、阶段 1：检查底座与运行环境

### 必读材料

README、AGENTS.md、frontend/package.json 和锁文件、backend/pom.xml、应用配置，以及相关架构、接口、数据库、页面和验证文档。历史验证只作参考。

### 操作

1. 列清已有能力、示例业务、待新增能力和需要退出的入口。
2. 该基线已有 Vue 门户/管理布局、Session 登录、角色权限、CSRF、统一请求响应、分页及示例记录 CRUD。
3. 注册、用户维护、上传、统计和选题业务按实际源码确认，不因菜单或文档存在就视为实现。
4. 核实 Java、Node/npm、Maven Wrapper、MySQL 的实际版本、路径和端口。现有 phpStudy 等服务可复用，不默认安装另一套数据库。
5. 核实已有库用途、登录方式和权限，不输出或保存真实密码。
6. 用 `npm ci` 安装锁定依赖，运行底座测试和构建。数据库测试使用独立库；记录跳过数量和原因。
7. 启动前后端，验证登录、刷新恢复、退出、双角色和示例 CRUD 持久化。

### 产出与出口

`docs/baseline.md`：来源版本、环境、已有能力、实际命令结果及问题。能解释底座边界，并区分已有问题与后续改动引入的问题。

## 四、阶段 2：确定选题与范围

### 操作

1. 未定题时，比较候选题的角色、主要实体、完整流程、页面量和外部依赖；按用户需要提供选题表。
2. 定题后明确项目名称、服务对象、角色、门户功能、管理功能及本期边界。
3. 至少写出一条有开始、业务动作和结束状态的完整流程，例如“申请 → 审核 → 执行 → 完成”。
4. 写清是否需要注册、上传、支付、短信、地图、审批等，模拟外围服务明确标注。
5. 更新 README、项目说明；候选资料按用户要求保留或移除，不再作为业务约束。

### 产出与出口

`docs/project.md`：选题、角色、实体、核心流程、范围内/范围外。用户已确定选题和交付范围。

## 五、阶段 3：编写可验收需求

### 操作

1. 按角色列功能，使用 FR 编号；每项写清入口、输入、权限、规则、结果及失败反馈。
2. 对订单、申请、预约等列状态流转表：原状态、操作者、动作、前置条件、目标状态、撤销与重复操作规则。
3. 明确时间窗口、金额计算、数量限制、归属、删除/停用、历史快照、并发和幂等的业务含义。
4. 列页面清单、数据实体和敏感字段，明确公开与登录后访问边界。
5. 用 AC 编号定义验收条件，覆盖正常链路、越权、非法参数、无效状态和实际相关的竞争场景。
6. 将未决定的建议默认值标明为待确认；已确认后同步到执行基线。

### 产出与出口

`docs/requirements.md`：范围、FR、状态机、规则、页面、数据及 AC。每个核心功能都有可执行验收条件，不把建议当作已确认决定。

## 六、阶段 4：确认视觉与页面基准

### 操作

1. 页面清单确定后制作关键页面或逐页效果图；需要生图时先做视觉预览。
2. 确定品牌、配色、字体、间距、卡片、导航、状态、表单与响应式原则。
3. 门户围绕用户操作，管理端围绕数据维护与业务处理，分别布局并共享基础组件。
4. 归档素材、来源和页面映射，记录图片中错误的文字、状态、数据与交互。
5. 规定视觉参考与需求冲突时服从需求，不能把整页效果图当成可交互页面。
6. 图片仅作环境示意时明确说明；实际内容和统计接入真实数据。

### 产出与出口

`参考素材/页面效果图/README.md`、图片及 `docs/pages.md`。后续开发知道每页参考哪张图、需要哪些真实交互。

## 七、阶段 5：制定计划与跟进机制

### 操作

1. 将需求拆成可独立检查的任务，写明前置依赖、变更范围、负责人、验收出口和证据位置。
2. 任务覆盖环境、公共契约、数据库、身份、核心业务、门户、管理、统计、示例退出、测试和交付。
3. 先完成一条贯通数据库、接口和页面的最小业务链，再扩展其他功能。
4. 确认哪些旧数据必须保留、数据库是否已存在，以及新建、升级和恢复方案。
5. 只有用户授权或适用规范要求时才进行多智能体分工；先固定契约，再划分文件责任，主负责人验收集成结果。
6. 明确范围和计划后保存执行版，不反复确认常规实现细节。

### 产出与出口

`docs/development-plan.md` 与 `docs/development-progress.md`。

进度最小模板：

```text
任务编号/名称：
关联需求与验收：
负责人/前置依赖：
状态：待开始 / 开发中 / 待联调 / 待验收 / 已完成
开始与完成日期：
变更范围：
实际验证命令与证据：
问题、未验证项与下一步：
```

## 八、阶段 6：建立工程契约和数据库

### 操作

1. 统一项目名、包名、构建产物、页面标题、菜单和演示文案，避免无业务必要地升级依赖。
2. 沿用 `/api`、`/api/admin`、`code/message/data`、既有分页及字符串 BIGINT ID 约定。
3. 明确字段、枚举、时间/时区、错误码、权限、动作接口、分页和筛选语义。
4. 为业务实体建立独立表，设计唯一约束、外键或一致性规则、索引及历史快照。
5. 根据真实风险选择事务、条件更新、锁和幂等，不照搬其他选题的锁方案。
6. 新库使用 schema 和演示数据；旧库使用顺序迁移。先备份并验证可恢复，保留要求保留的数据。
7. 检查实际 MySQL 版本支持情况；不把 CHECK 等约束作为唯一业务校验。
8. 凭据通过环境变量或交互提供；运行和测试账号分别限制权限，忽略本地敏感文件。

### 产出与出口

更新 architecture、contracts、database 文档及 SQL。结构、实体、接口和前端字段一致，初始化与升级路径明确。

## 九、阶段 7：按完整业务链开发

### 每条业务链的固定循环

1. 阅读关联 FR、AC、状态机与页面基准。
2. 实现数据库查询与受控输入，后端完成权限、归属、规则和事务。
3. 在 api 模块封装请求，页面调用统一方法。
4. 接入真实列表、详情、表单和动作，验证写入后刷新仍存在。
5. 补加载、空数据、校验、提交中、成功、业务失败和网络失败反馈。
6. 验证正常流程及关键边界，修复后更新文档、进度并形成可评审提交。

### 实现检查

- 当前用户、归属、角色和计算金额由后端决定，不能信任客户端。
- 管理接口在后端验证角色；本人数据在查询阶段限制范围。
- 状态动作使用明确接口，不开放任意改状态绕过业务规则。
- 沿用 Session、BCrypt、CSRF；登录退出刷新 CSRF，刷新通过 me 恢复身份。
- 401 清理身份并引导登录，403 明确提示；写请求失败不自动重放。
- 搜索参数化、排序白名单，输入校验类型、长度、范围及未知字段。
- 筛选回第一页，删除后处理空页；失败保留表单，提交防重，删除有确认。
- 定时业务验证边界、重复执行和启动补处理；测试时钟隔离在测试环境。
- 统计与首页数据来自真实业务查询，不能以固定数字冒充实时结果。

### 产出与出口

每条链路都能从页面操作到持久化结果；未接真实接口的页面保持开发中状态。其他功能按同一循环推进。

## 十、阶段 8：退出示例并同步文档

1. 移除无关示例菜单、路由、页面、API、提示和框架宣传。
2. 旧表和数据按已确认的迁移方案处理，不因移除入口而自动删表。
3. 替换依赖旧业务的测试，保留仍适用的身份、安全和请求测试。
4. 准备与选题一致的演示角色、图片、数据、多个状态及完整流程。
5. 同步 README、需求、架构、接口、数据库及页面说明。

出口：项目名称、页面、接口和数据共同表达当前业务，未破坏要求保留的历史数据。

## 十一、阶段 9：分层验收与修复

| 层次 | 必查内容 | 证据 |
|---|---|---|
| 前端 | 身份、跳转、请求竞争、关键表单及业务交互 | 测试输出、构建结果 |
| 后端 | 参数、权限、归属、状态、时间和业务计算 | 相关测试报告 |
| MySQL | 约束、事务、并发、回滚及持久化 | 隔离库集成报告 |
| 迁移 | 新库初始化、旧库升级、重复执行、备份恢复 | 前后数量/字段核对 |
| 浏览器 | 双角色完整流程、加载空错、401/403及实际相关冲突 | 步骤、截图与结果 |
| 布局 | 约定桌面和窄屏、表格与弹窗 | 必要截图及问题修复 |
| 性能 | 需求规定的数据量、并发、采样与指标 | 环境及原始结果 |
| 交付 | 构建、JAR启动、正常时间/配置及冒烟 | 包信息、命令与结果 |

执行要求：

- 测试库显式隔离，清理只涉及本次数据；不要在演示库或真实业务库执行破坏性测试。
- 不同账号用独立会话或先退出，防止 Cookie 混淆。
- 先运行相关检查，再完成项目规定的全量测试与构建；没有新变化或疑点不重复扩张测试。
- 性能先约定数据量、并发、P95 等目标，再测量；预期业务冲突与系统错误分别统计。
- 测试缺配置导致跳过，不能写成全量通过；静态检查不能写成浏览器验收。
- 布局按约定尺寸验证，发现问题针对性复测；用户要求停止追加检查时记录覆盖范围与限制。

产出：`docs/verification.md`，需要时另附 browser-verification、upgrade-verification、performance。每项记录日期、环境、命令、通过/失败/跳过和限制。

## 十二、阶段 10：构建、交付与使用教程

### 操作

1. 执行前端测试与构建、后端测试与打包，核对实际报告数量和跳过项。
2. 使用最终 JAR 启动，执行登录、角色、公共查询和核心业务冒烟；不要只验证开发启动方式。
3. 确认测试接口、测试时钟及测试配置未进入生产包或正常演示环境。
4. 恢复正常数据库、时间、端口和代理；交付时实际核实入口，不把历史运行状态当作当前状态。
5. 编写启动说明、逐功能使用教程、完整演示顺序及排错说明。
6. 提供本地演示账号，真实数据库凭据和令牌不进入交付文档。
7. 检查 Git 工作区、忽略文件和差异；按授权完成提交、PR或推送，避免推错底座远程。
8. 报告已完成内容、实际验证、未解决问题和未验证范围；核心链路通过才称可演示。

### 交付清单

- 前后端源码及锁定依赖。
- 新库 SQL、演示数据、必要迁移与备份恢复说明。
- 自动化测试及需求要求的性能脚本。
- 前端产物与后端 JAR 的构建/获取说明。
- README：环境、配置、建库、启动、入口、账号、测试命令。
- 最新业务、接口、数据库和页面文档。
- 使用教程、演示指南、实际验收记录与限制。

## 十三、可直接复用的执行指令

### 检查底座

> 检查当前 graduation-project-starter 的规范、依赖、源码和文档，记录基线提交与环境。区分已有能力、示例业务和缺失能力，运行可执行的基线检查，不改业务范围，不覆盖已有数据。

### 定义需求

> 为【选题】编写需求说明书，明确角色、门户/管理功能、实体、状态流转、业务规则和验收标准。影响业务含义或交付范围的缺口尽早询问；默认值标为建议，不当成已确认决定。

### 确定视觉

> 根据已确认需求制作【页面范围】的视觉方案，先不写业务代码。归档素材、来源、页面映射和制作规范，记录效果图中需要校正的业务内容。

### 制定计划

> 根据现有资料制定可执行开发计划，覆盖依赖、任务、数据库迁移、完整业务链、测试、浏览器验收和交付。确认后保存计划及进度表。多智能体仅在明确授权后使用，并先约定公共接口与文件责任。

### 持续实施

> 按确认版计划和进度表继续，优先完成真实业务链。同步代码、SQL与文档，执行相关检查并记录证据；遇到环境缺失继续独立任务，不以代码已写代替验收完成。

### 收尾交付

> 按验收标准复核功能、安全、数据、迁移、测试、构建和浏览器流程。基于最终产物检查启动，交付使用教程、账号、演示顺序及真实限制，并核对工作区和远程用途。

使用方式：每次新项目从阶段 0 开始；接续项目先读计划、进度和当前差异，从尚未满足出口的阶段继续，不重复初始化或重做已有成果。
